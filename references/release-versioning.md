# 发布版本号规则

发布方案冻结前，根据相对上一正式版本的完整用户可见变化选择 `MAJOR.MINOR.PATCH`，不按提交次数、调试轮次或打包次数递增。

| 级别 | 判断依据 | 示例 |
|---|---|---|
| 大版本 MAJOR | 不兼容的 API/数据/配置契约，或需要明确迁移的核心产品与工作方式重构 | `1.6.4 → 2.0.0` |
| 中版本 MINOR | 向后兼容的新功能、新模块、完整新场景，或现有能力的显著扩展 | `1.6.4 → 1.7.0` |
| 小版本 PATCH | 已有功能的错误修复、局部交互打磨、性能与安全修补，未引入完整新能力 | `1.6.4 → 1.6.5` |

- 同次发布含多类变更时取最高级别。新增工作台、完整会话能力等不能因附带 UI 修复而降为 PATCH；也不为单个文案或间距调整强行升中版本。
- 升 MAJOR 时 MINOR/PATCH 清零；升 MINOR 时 PATCH 清零。`0.x` 开发期仍以中版本区分新模块与主要能力扩展，例如 `0.4.28 → 0.5.0`；首次稳定版 `1.0.0` 需有明确的稳定性与兼容承诺，不自动凑整数。
- 用户明确指定版本或已有项目/商店规则时优先遵循，并在发布方案写明依据；不要用统一规则覆盖独立服务的版本策略。
- 预发可用 `-rc.N` / `-beta.N`；平台不支持时用独立构建号与 source commit 区分。反复修复、重建和预发验收不连续消耗正式 PATCH 号。
- 发布方案记录上一正式版本、目标版本、级别及理由、兼容性/迁移影响。候选被冻结后若范围变化，重新判断级别并更新同次发布的全部版本入口。
- 同一客户端产品按项目实际约定核对包版本、lockfile、原生元数据、更新清单、Git tag、更新说明与官网下载入口；平台构建号单独管理。Web 也应能通过产品版本和 source commit 追溯，不能只改页面文案。
- 已公开版本和版本化下载对象保持不可变，不用同版本替换不同二进制。未发布草稿可撤回并改为正确版本；上线后发现问题发布新的适当级别版本或按方案回滚。
