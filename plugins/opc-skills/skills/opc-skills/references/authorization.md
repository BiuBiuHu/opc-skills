# 授权、审核与重复确认

工作模式、文档规范和发布流程使用本参考判断是否需要用户输入。它统一授权判断，不替代测试、候选冻结、发布完整性和真实验收。

## 先检查已有授权

核对当前目标、动作、系统范围、环境、数据副作用、费用和候选版本，引用用户指令或已批准方案作为授权来源。

- 用户已明确要求实现、修复、迁移、合并或发布到指定环境时，在该范围内完成准备、实施和验证，不因换阶段、补文档、创建 PR 或读取另一个 reference 再问一次。
- 补写技术记录、测试报告和已有候选的验证结果，不产生新授权，也不使已有授权自动失效。
- 模式是执行方式，不是额外权限。`manual-gated` 在尚未获准进入实施/外部动作时等待；明确实施指令、implementation-loop 和 bug 修复沿用已有授权。`full-auto` 仍需用户明确选择，不越过用户指定的“方案先审核”或生产约束。
- 用户只要求分析、方案、review 或 validation-only 时，不进入编码、迁移或部署。用户明确要求“方案先给我看”时等待该审核，通过后不为同一实施动作再问。
- Skill、模板和子代理结果不能自行批准用户未授权的动作。Inbox/Todo 不为无关新任务自动授予权限。

## 只询问缺失或改变的部分

| 情况 | 动作 |
|---|---|
| 同一目标、范围、环境、风险和候选，已有明确授权 | 引用来源并继续技术检查 |
| 尚未批准实施，或用户明确保留审核关卡 | 给出可审方案，等待进入对应阶段 |
| “部署/发布”没有环境且上下文无法确定 | 补充预发还是生产，不执行依赖该答案的部署 |
| 只批准 Preview | 不推定 Production 授权；已有独立明确生产授权则复用 |
| 系统、环境、迁移/不可逆副作用、费用或风险扩大 | 对新增部分取得授权，独立工作可继续 |
| 冻结候选 commit、构建映射、alias 或发布顺序改变 | 按发布规则重新评审受影响候选，不套用旧批准 |
| 仅回填事实、格式和已有候选的验证结果 | 不创建新的审批关卡 |
| 只讨论 Subagent 接口，没有允许实际使用子代理 | 不启动子代理 |

没有回答、超时、工具预选或代理自行写出的 `approved` 都不是批准。缺少授权时停止依赖该授权的动作，继续可独立完成的分析和可审准备；提问时说明原授权、具体缺口和后果。

## 授权与技术门禁分别核对

生产仍要求批准的目标与冻结候选、隔离预发、测试报告、CR、默认分支归并、部署来源映射、关联系统矩阵、真实回归/账号/探针/DB after/日志/漂移和 worktree 归位。适用证据不全时 Release PR 保持 open。授权不能代替技术检查，技术通过也不能代替授权。

发布方案继续使用 `awaiting-review / approved / rejected`。已有有效批准可直接引用并记录 `approved`；不因新建记录而强制从等待开始。Preview 和 Production 分别记录；范围或候选改变仍使受影响审批失效。

## 最小授权记录

在本次方案、实施记录或发布方案复用同一记录，不为每个 reference 另建审批：用户指令/批准来源与日期；动作、环境、系统和数据范围；方案/冻结候选及费用、副作用边界；沿用的授权或新增缺口；技术检查和残余风险。
