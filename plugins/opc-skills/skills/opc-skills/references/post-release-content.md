# 发布后内容生产

本参考用于在页面或功能发布完成后，按需把本次交付整理成可搜索、可引用、可复用的技术文章。它是发布完成后的可选旁路，不改变页面发布的成功条件，也不替代 Code Review、预发验证、线上回归或 Release PR 核销。

## 1. 触发和模式

生产发布完成后，主 Agent 必须检查项目是否启用发布后内容生产，并在最终回复中给出可选项：

- `suggest`：从本次交付提炼 3-5 个候选选题，只生成选题清单。
- `draft`：自动采集素材，生成中文稿和英文稿，落盘后进入内容审核。
- `publish`：在 `draft` 通过后，按项目内容仓库和部署流程发布文章。必须明确目标站点、内容目录、构建命令和发布环境。

默认模式是 `suggest`。用户明确说“写文章”“生成发布文章”“按这次发布写一篇”时进入 `draft`；只有用户明确批准文章发布，或项目事实源已配置 `autoPublish: true` 且包含独立的文章发布门禁时，才能进入 `publish`。

项目事实源可以用以下配置驱动自动化行为，真实博客路径和命令必须保存在项目事实源中，不写入通用 skill：

```yaml
postReleaseContent:
  enabled: true
  defaultMode: suggest
  autoDraft: false
  autoPublish: false
  blogRoot: <PROJECT_FACTS>
  buildCommand: <PROJECT_FACTS>
  publishCommand: <PROJECT_FACTS>
```

当 `enabled: true` 且发布状态进入 `complete` 时，主 Agent 必须自动检查配置并提供内容选项；只有 `autoDraft: true` 才能在无额外口令时自动生成草稿。`autoPublish` 不能单独解除人工审核、目标环境确认、预览验证和文章发布门禁。

文章生产不能因为页面发布完成而静默公开，也不能把文章发布失败当作页面发布失败。文章有独立状态：

```text
disabled -> suggested -> drafted -> content-reviewed -> published
```

## 2. 素材采集

文章中的数字、版本、时间线、技术决策和问题根因必须来自第一手材料，不能凭记忆或直接复制已有文章。

按以下优先级采集：

1. Git 提交记录、PR/CR 和变更统计。
2. 代码、测试、配置 schema 和架构调用图。
3. `docs/<FEATURE_NAME>/` 下的 PRD、变更影响、测试报告、联调报告、发布方案和 evidence manifest。
4. 页面截图、运行时快照、接口响应和日志摘要。
5. 已有文章只用于发现选题，事实必须回到以上来源核实。

建议先运行：

```bash
./scripts/prepare_post_release_content.sh \
  <PROJECT_ROOT> <FEATURE_NAME> <BASE_COMMIT> <HEAD_COMMIT>
```

脚本只生成本地素材清单，不会提交、部署或发布文章。素材清单生成后，必须检查是否包含账号、token、密钥、内部域名、客户数据、数据库连接信息或不可公开的截图。

## 3. 选题

每个候选选题都要能转成别人会搜索的具体问题，而不是只写产品发布公告。优先选择：

- 有明确问题、决策或故障根因的主题。
- 有可验证数字、前后对比或代码证据的主题。
- 能回答“为什么这样做”“怎么排查”“如何避免”的主题。
- 与本次发布真实相关、但不暴露项目事实的通用经验。

候选表至少包含：

| 标题 | 搜索问题 | 一手素材 | 差异化 | 优先级 | 建议切入角度 |
|------|----------|----------|--------|--------|--------------|
| | | | | P0/P1/P2 | |

如果用户没有指定文章主题，`suggest` 输出 3-5 个候选标题；`draft` 可以选择最高优先级主题，但必须记录选择依据。

## 4. 写作要求

- 开头前两句直接给结论，不先铺垫项目背景。
- 首次出现的术语用一句话定义。
- 结构优先使用“问题 -> 方案 -> 验证 -> 结论”或“是什么 -> 为什么 -> 怎么做”。
- 保留第一手经验、具体数字、失败路径和可复核证据。
- 中文稿目标不少于 1500 字；素材不足时标记缺口并继续回到素材源挖掘，不用空话补长度。
- 删除宣传腔、模板化转折、重复结论、过度排比和不必要的破折号。
- 允许保留作者的第一人称判断，但不能捏造个人经历或没有证据的结论。

文章中不得出现：

- 真实账号、邮箱验证码、token、密钥或环境变量值。
- 内部域名、deployment URL、数据库 host/schema、客户数据或未公开接口。
- 仅凭截图推断出的未验证数字。
- 把预发结果写成生产结果，或把单页 smoke 写成全链路通过。

## 5. 双语和排版

一次 `draft` 默认同时产出中文和英文两版。英文稿不是逐句翻译，而是按英文读者重写：

- 中文稿强调实践上下文和具体过程。
- 英文稿使用主动语态、短段落和英文搜索词。
- 两版共享已核实的数字、版本、架构边界和验证结论。
- 标题、摘要和关键词分别按中文和英文搜索习惯改写。

如果目标仓库是 Astro 博客，使用项目事实源指定的内容目录和 frontmatter；通常为：

```text
src/content/blog/<slug>.md
src/content/blog/<slug>-en.md
```

如果项目不是 Astro，不得强行创建该目录。使用 `<PROJECT_ROOT>/docs/<FEATURE_NAME>/07-content/` 作为默认落盘位置，并在内容生产记录中写明后续发布适配动作。

正文排版要求：

- H1 只由 frontmatter 标题承担，正文从 H2 开始。
- 每 300-500 字左右用标题切分。
- 步骤、对比和验收结果优先使用列表或表格。
- 命令和代码使用带语言标识的 fenced code block。
- 架构、调用链和状态机优先使用 Mermaid。
- 截图必须有来源、状态、脱敏说明和 alt 文本。

## 6. SEO/GEO 和配图

frontmatter 至少包含：

```yaml
title: ...
date: YYYY-MM-DD
excerpt: ...
category: ...
lang: zh-CN
```

英文版将 `lang` 改为 `en`，`excerpt` 使用英文关键词。摘要应短、具体、可独立理解，中文不超过约 150 字，英文不超过约 160 个字符。

配图按信息价值排序：

1. 真实问题截图或修复前后对比，必须脱敏。
2. Mermaid 架构图、流程图或状态图。
3. 封面图或 OG 图，仅作为分享卡片，不替代正文证据。

不要为了装饰堆图片。没有可靠截图时，宁可使用 Mermaid 或明确写出“此处缺少可公开证据”，不要生成伪造的故障截图。

## 7. 自动化执行闭环

启用 `draft` 后按以下顺序执行：

1. 确认生产发布已完成，并读取发布方案、测试报告和证据清单。
2. 运行素材准备脚本，记录 base/head commit 和变更范围。
3. 从 Git、代码和文档中整理事实清单。
4. 生成候选选题并记录选题决策。
5. 生成中文稿、英文稿、frontmatter、配图计划和引用/证据清单。
6. 写入 `07-content/` 或项目事实源指定的博客目录。
7. 做去 AI 味、敏感信息、事实一致性、链接和 Markdown 检查。
8. 更新 `content-production.md`，状态设为 `content-reviewed` 前等待内容审核。
9. 只有进入 `publish` 后，才执行博客构建、预览、Code Review、部署和发布后验证。

内容生产失败时保留已生成的素材清单和失败原因，允许从最近一个成功阶段重试，不重复执行已经完成的昂贵步骤。
